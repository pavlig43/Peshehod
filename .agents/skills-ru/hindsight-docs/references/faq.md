<a id="what-is-hindsight-and-how-does-it-differ-from-rag"></a>
### Что такое Hindsight и чем он отличается от RAG?

Hindsight — система долгой памяти для ИИ-агентов с устройством по образцу биологической памяти. В отличие от обычного RAG (генерации с поиском данных), Hindsight:

- **Хранит структурные факты**, а не фрагменты исходных документов.
- **Строит ментальные модели**, которые со временем обобщают знания.
- **Связывает сущности и понятия графом**.
- **Учитывает время** при поиске и выводе.
- **Учитывает черты поведения** при рассуждении, чтобы точнее отвечать.

Подробное сравнение — в разделе [«RAG и память»](developer/rag-vs-hindsight.md).

<a id="why-use-hindsight-instead-of-other-solutions"></a>
### Зачем брать Hindsight вместо других решений?

Hindsight создан именно для памяти агентов. Его сильные стороны:

- **Высокая точность**: первое место в тестах LongMemEval для памяти агентов (см. [результаты](https://benchmarks.hindsight.vectorize.io/)).
- **Проверенная основа**: PostgreSQL — надёжная и хорошо изученная база.
- **Устройство для облака**: рассчитан на работу в облаке с ростом числа экземпляров.
- **Разные способы запуска**: свой сервер или Hindsight Cloud; работает с любым поставщиком LLM.
- **Долгая память**: не только находит данные, но и строит ментальные модели, которые обобщают знания со временем.
- **Рассуждение по графу**: знает связи между сущностями и понятиями.
- **Готов к рабочей нагрузке**: масштабируется до миллионов воспоминаний; recall занимает 50–500 мс.
- **Прост для разработчика**: API retain, recall и reflect; SDK для Python, TypeScript, Go и Rust; подключения к LiteLLM и Vercel AI SDK.

Базы векторов дают лишь поиск, а RAG — поиск документов. Hindsight даёт **память, которая меняется вместе с пользователем**.

<a id="what-are-zombie-operations-and-how-do-i-recover-them"></a>
### Что такое «зомби-операции» и как их вернуть к работе?

**Зомби-операция** — фоновая задача, которая навсегда осталась в состоянии `processing`, потому что взявший её обработчик уже не работает. Часто это случается после перезапуска контейнера Docker. Признак: счётчик `pending_consolidation` (или похожий) на `/banks/{bank_id}/stats` не падает, хотя по журналу у обработчика есть свободные места.

Обычно причина — непостоянный `HINDSIGHT_API_WORKER_ID`. По умолчанию обработчик берёт имя узла контейнера, а Docker меняет его после каждого перезапуска. Новый контейнер получает иной ID и не считает задачи старого обработчика своими.

**Чтобы вернуть задачи**, запустите команды администратора:

```bash
# If you know which worker is dead:
hindsight-admin decommission-worker <old-worker-id>

# Or, fleet-wide release across all workers:
hindsight-admin decommission-workers
```

**Чтобы предотвратить сбой**, задайте постоянный `HINDSIGHT_API_WORKER_ID` (через Docker `-e HINDSIGHT_API_WORKER_ID=...` либо `--worker-id` на своём сервере). Схема Helm уже делает это: StatefulSet сам ставит имя пода.

Полный порядок поиска и устранения сбоя — в разделе [«Команды администратора — восстановление зависших операций»](developer/admin-cli.md#recovering-stuck-or-zombie-operations).

<a id="how-do-i-isolate-user-data"></a>
### Как разделить данные пользователей?

**Банк памяти** — отдельное хранилище («мозг») со своими воспоминаниями, сущностями, связями и, по желанию, чертами поведения (скептицизмом, буквальностью, эмпатией). Банки полностью отделены друг от друга; данные между ними не смешиваются.

Для приложения с несколькими пользователями есть два подхода:

**1. Отдельный банк на пользователя** (подходит чаще всего)
- Создайте по банку на пользователя, например `bank_id="user-123"`.
- Это проще всего настроить и даёт самое строгое разделение данных.
- Удобно для личных запросов и ответов с учётом пользователя.
- В каждом банке могут быть свои черты поведения и исходный контекст.
- **Ограничение**: нельзя анализировать всех пользователей вместе, например узнать самую частую тему среди них.

**2. Один банк с тегами** (если нужен общий анализ)
- Возьмите один банк для всего приложения.
- При retain ставьте на воспоминания ID пользователя, например `tags={"user_id": "user-123"}`.
- При recall/reflect отбирайте по тегам записи нужного пользователя.
- **Плюс**: доступны и личные, и общие запросы, например анализ одного пользователя или сводка по всем.

Для простоты и защиты личных данных берите отдельные банки. Если нужны выводы по всем пользователям, берите общий банк с тегами. Управление описано в разделе [«Банки памяти»](developer/api/memory-banks.md).

<a id="whats-the-difference-between-retain-recall-and-reflect"></a>
### Чем отличаются retain, recall и reflect?

У Hindsight три основные операции:

- **Retain**: хранит данные — факты, сущности и связи.
- **Recall**: ищет и возвращает исходные данные памяти по запросу.
- **Reflect**: через ИИ-агента отвечает на вопрос с опорой на найденную память.

Подробнее об API — в разделе [«Операции»](developer/api/operations.md).

---

<a id="when-should-i-use-recall-vs-reflect"></a>
### Когда брать recall, а когда reflect?

**Берите recall, если:**
- Нужны исходные факты для своего рассуждения или запроса к модели.
- Вы хотите сами решать, как толковать воспоминания.
- Нужно найти простой факт, например «Что Алиса сказала об X?».
- Важна скорость: recall заметно быстрее (50–500 мс против 1–10 с).
- Вы хотите сами собрать ответ из найденных воспоминаний.

**Берите reflect, если:**
- Нужен готовый ответ на основе памяти без лишнего вызова LLM.
- Ответ должен учитывать черты банка: скептицизм, буквальность и эмпатию.
- Вопрос требует вывода в несколько шагов по фактам, наблюдениям и ментальным моделям.
- Нужен структурный ответ через `response_schema`.
- Нужны ссылки на основания ответа: reflect возвращает список взятых воспоминаний, ментальных моделей и указаний.

**Главное различие**: recall возвращает данные, reflect — готовый ответ. Recall даёт материал, а reflect сам рассуждает с учётом черт банка и ищет в несколько шагов.

```
recall("What food does Alice like?")
→ ["Alice loves sushi", "Alice prefers vegetarian options"]   # raw facts

reflect("What should I order for Alice?")
→ "I'd recommend a vegetarian sushi platter — Alice loves sushi and prefers vegetarian options."  # grounded answer
```

Полное описание API см. в разделах [«Recall»](developer/api/recall.md) и [«Reflect»](developer/reflect.md).

<a id="when-should-i-use-mental-models"></a>
### Когда нужны ментальные модели?

**Ментальные модели** — устойчивые знания, которые со временем складываются из отдельных фактов. Они нужны для:

- Понимания общих закономерностей, а не отдельных фактов, например «Пользователь предпочитает функциональный стиль программирования».
- Долгих закономерностей в поведении, например «Клиент следит за ценой, но ценит качество».
- Контекста для рассуждения ИИ-агента в операциях **reflect**.

Ментальные модели создаются сами при retain и помогают reflect давать более полные ответы с учётом контекста. См. [«Ментальные модели»](developer/api/mental-models.md).

<a id="does-hindsight-support-metadata-filtering"></a>
### Можно ли отбирать записи по метаданным?

Да — с помощью **тегов**. Теги — строковые метки, которые прикрепляют к воспоминаниям при retain и применяют как фильтр при recall/reflect. Возвращаются только воспоминания с подходящим тегом.

```python
# Tag memories at retain time
client.retain(bank_id="my-bank", items=[{
    "content": "...",
    "tags": ["user:alice"],
}])

# Filter by tag at recall time
client.recall(bank_id="my-bank", query="...", tags=["user:alice"])
```

Подробности, включая теги уровня документа, — в разделе [«Теги»](developer/api/retain.md#tags-and-document_tags).

**А можно ли отбирать по сущностям?**

Сущности (люди, места, понятия), извлечённые из воспоминаний, хранятся в графе знаний и помогают поиску по графу. Поэтому запрос «расскажи об Алисе» сам найдёт связанные с Алисой воспоминания без ручного фильтра.

Если нужен явный отбор по тегам со значениями сущностей, возьмите **метки сущностей** с `tag: true`. Они позволяют задать строгий набор меток `key:value` (например, `user:alice`, `topic:algebra`), извлекаемых при retain. С `tag: true` каждое найденное значение также записывается как тег единицы памяти, после чего его можно отбирать через обычные `tags`/`tags_match`:

```python
# Bank config: entity label group with tag: true
{
    "entity_labels": [{
        "key": "user",
        "type": "text",
        "tag": True,
        "description": "The user this memory belongs to"
    }]
}

# The label "user:alice" is extracted and also written as a tag
# Filter at recall time using the standard tags parameter
client.recall(bank_id="my-bank", query="...", tags=["user:alice"])
```

Настройка описана в разделе [«Метки сущностей»](developer/retain.md#entity-labels).

**А как работают `metadata` у документа?**

Метаданные документа (пары ключ–значение `metadata` в элементе retain) нужны для другого. Они:
- **Попадают в запрос на извлечение фактов**, чтобы LLM видела лишний контекст. Например, заголовок или источник документа может повысить точность.
- **Возвращаются без правок с каждым найденным воспоминанием**, чтобы приложение могло связать его с источником по адресу, ID беседы или номеру обращения без ещё одного поиска.

Метаданные не работают как фильтр. Если recall должен искать лишь в части документов, берите теги.

<a id="how-do-i-control-which-types-of-memories-are-recalled"></a>
### Как выбрать виды воспоминаний для поиска?

Если в банке есть записи разной формы (скажем, краткие правила и подробные процедуры), а recall возвращает не ту форму, помечайте факты при retain через **метки сущностей** с `tag: true`, а при recall ставьте строгий фильтр.

1. Задайте для банка группу меток с `tag: true` и строгим набором значений, например `rule` и `procedure`.
2. Вызовите retain как обычно: LLM сама отнесёт каждый найденный факт к виду.
3. При recall передайте `tags=["memory_type:rule"]` и `tags_match="any_strict"`, чтобы вернуть лишь совпадающие воспоминания.

Фильтр работает на уровне SQL до сортировки, а не просто меняет оценку близости. Исключённые воспоминания вообще не попадут в поиск. Это надёжнее правки весов сортировки, которая лишь меняет баллы и не может дать строгий порядок.

Полный пример — в разделе [«Советы по работе — отбор по форме памяти»](best-practices.md#filtering-by-memory-shape-with-entity-labels), настройка — в разделе [«Метки сущностей»](developer/api/memory-banks.md#entity-labels).

<a id="what-is-the-recommended-format-for-retaining-conversations"></a>
### В каком виде лучше сохранять беседы?

Передавайте **всю беседу одним документом** и обновляйте его по мере роста беседы. Hindsight сам разобьёт текст на части.

**Лучший формат — массив JSON:**

```json
[
  {"role": "user",      "content": "I moved to Berlin last month."},
  {"role": "assistant", "content": "How are you finding it?"},
  {"role": "user",      "content": "Love it, especially the food scene."}
]
```

Hindsight лучше разбивает массивы JSON на части, потому что в таком виде беседы встречаются чаще всего.

**Другой вариант — обычный текст с префиксами:**

```
[2025-06-01T10:32:00Z] user: I moved to Berlin last month.
[2025-06-01T10:32:05Z] assistant: How are you finding it?
[2025-06-01T10:32:20Z] user: Love it, especially the food scene.
```

Имя участника и время в начале каждого сообщения повышают качество извлечения: LLM точнее понимает, кому принадлежит факт и когда он произошёл.

**Для обновления берите постоянный ID документа:**

```python
await client.retain(
    bank_id="my-bank",
    documents=[{
        "id": "chat-session-abc123",  # stable ID enables upsert
        "content": conversation,       # full conversation so far
    }]
)
```

Повторная запись с тем же `id` заменит старый документ и его факты. По мере роста беседы повторы не будут накапливаться.

**Не делайте сводку и не извлекайте факты заранее.** Hindsight делает это сам, а для верного вывода ему нужна полная беседа. Реплика «да, именно» или «выберу второй вариант» без соседних сообщений не имеет смысла.

<a id="how-is-hindsights-graph-different-from-a-traditional-knowledge-graph"></a>
### Чем граф Hindsight отличается от обычного графа знаний?

Hindsight строит **граф вокруг событий**: бесед, наблюдений и воспоминаний, а не вокруг отдельных неизменных фактов. Основой служат воспоминания. Сущности привязываются к воспоминаниям, где они встречаются; сами воспоминания тоже могут быть связаны друг с другом. Представьте карту и альбом с записями.

**Обычный граф (например, Neo4j) — карта.** Он показывает прямые связи между местами как дороги, описывая строгие факты об устройстве мира:

```
[Toronto] ──IS_IN──> [Canada]
```

**Граф Hindsight — альбом.** Каждая страница — одно воспоминание. На странице стоят метки всех людей, понятий и других названий, которые встретились в тот момент. Метки не соединены друг с другом напрямую: они просто живут на одной странице.

```
Scrapbook page: "Math Class"
  [Alice]   [Acme]   [pedagogy:scaffolding]
```

#### Как они учитывают перемены со временем?

Здесь при работе с памятью ИИ у обычных графов возникают большие трудности.

**Обычному графу трудно отражать перемены.** Если Алиса уходит из Acme Corp в Stark Industries, старую стрелку `[WORKS_AT]` нужно вручную удалить или переписать. Иначе граф будет утверждать, что она работает в обоих местах сразу. Обычные графы описывают текущий момент и теряют историю при смене данных.

**Hindsight хранит историю и потому легко отражает перемены.** Если Алиса меняет работу, прошлое не переписывают. Добавляют новую страницу альбома — `Memory: Tuesday's Call` с меткой `[Stark Industries]`. Прошлогодняя страница по-прежнему верно связывает её с `[Acme Corp]`. Граф хранит смену событий без сложной ручной правки базы.

#### Откуда берутся метки и как ими управлять?

Метки появляются благодаря ИИ и настройкам разработчика:

- **Автоматический поиск сущностей (по умолчанию):** цепочка LLM в Hindsight сама находит в тексте людей, места, даты и другие общие сущности, а затем превращает их в метки.
- **Управление через `entity_labels`:** вы можете задать свою схему с помощью [меток сущностей](developer/retain.md#entity-labels). Тогда LLM будет раскладывать воспоминания по заранее заданным названиям и значениям. Вместо случайных описаний от ИИ вы сами выбираете метки. Например, для ключа `pedagogy` разрешите лишь `scaffolding`, `direct_instruction` и `socratic_questioning`. Чтобы оставить **только** заданные метки и выключить свободное извлечение сущностей, поставьте в настройках банка `entities_allow_free_form: false`. После этого LLM будет выдавать лишь записи из вашей схемы.

#### Можно ли связать сущности напрямую друг с другом?

Нет. В Hindsight между сущностями (людьми, местами, понятиями и метками групп) нет прямых стрелок. Они связаны тем, что привязаны к одной единице памяти — одной странице альбома.

#### Как Hindsight находит связи без прямых рёбер между сущностями?

Сначала recall ищет по смыслу и берёт самые близкие к запросу воспоминания как начальные страницы. Затем расширяет поиск по трём видам связей:

- **Общие сущности.** Если воспоминания A и B связаны с одним узлом сущности, например `[pedagogy:scaffolding]`, Hindsight проходит путь `Memory A → [pedagogy:scaffolding] → Memory B`. Это страницы с одной и той же меткой.
- **Смысловые связи воспоминаний.** При сохранении нового воспоминания Hindsight заранее находит ближайшие к нему векторы и связывает страницы с близким смыслом напрямую, даже без общей метки.
- **Причинные связи воспоминаний.** Hindsight также извлекает явные связи причин и следствий (`causes`, `caused_by`, `enables`, `prevents`) между воспоминаниями. Модели не приходится угадывать эти связи: они становятся рёбрами графа.

Поиск по смыслу выбирает начальные точки, а граф добавляет связи по самому сильному из трёх признаков для каждого кандидата.

#### Помогает ли такой граф снизить число выдумок агента?

Да: LLM получает контекст с лучшими основаниями для вывода. Три свойства модели альбома помогают напрямую:

- **История хранится, а не схлопывается.** Модель видит факты с привязкой ко времени: Алиса работала в Acme в прошлом году, теперь — в Stark Industries. Ей не приходится мирить два противоречивых ребра настоящего времени.
- **Связи взяты из записи, а не домыслены.** Recall возвращает пару связанных воспоминаний, потому что у них общая сущность, заранее найденная смысловая связь или явная связь причины и следствия. Связь видна в контексте, поэтому модели не нужно её придумывать.
- **Подтверждения накапливаются.** Несколько воспоминаний об одной сущности подкрепляют друг друга и дают модели обоснованный вывод вместо одного ничем не подкреплённого утверждения.

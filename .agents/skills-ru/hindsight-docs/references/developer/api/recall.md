# Извлечение воспоминаний: Recall

Извлекает воспоминания из банка с помощью нескольких стратегий поиска.

При вызове `recall` Hindsight параллельно применяет четыре стратегии — семантическое сходство, поиск по ключевым словам (BM25), обход графа и поиск по времени, — а затем объединяет результаты и пересортировывает их в единый список. Ответ содержит структурированные факты, а не исходные документы.

{/* Импорт исходных файлов */}

> **ℹ️ Как работает Recall**
>
> О четырёх стратегиях (семантический поиск, поиск по ключевым словам, по графу и по времени) и объединении RRF см. руководство [архитектуры Recall](../retrieval.md).

> **💡 Требования**
>
> Выполните инструкции [быстрого старта](./quickstart), чтобы установить клиент и запустить сервер.

## Простой запрос Recall

### Python

```python
response = client.recall(bank_id="my-bank", query="What does Alice do?")

# response.results — список объектов RecallResult с полями:
# - id:             идентификатор факта
# - text:           извлечённый факт
# - type:           "world", "experience" или "observation"
# - context:        метка контекста, заданная при retain
# - metadata:       dict[str, str], заданный при retain
# - tags:           список меток
# - entities:       имена сущностей, связанные с этим фактом
# - occurred_start: дата и время начала события в формате ISO
# - occurred_end:   дата и время окончания события в формате ISO
# - mentioned_at:   дата и время сохранения факта
# - document_id:    идентификатор документа, которому принадлежит факт
# - chunk_id:       идентификатор фрагмента, из которого извлечён факт
```

## Параметры

### query

Естественно сформулированный вопрос или утверждение для поиска. Это единственное обязательное поле. Запрос одновременно запускает все четыре стратегии: для семантического поиска он преобразуется в вектор, для BM25 — в набор токенов, используется для обхода графа и проверяется на наличие указаний времени. После поиска исходный текст запроса также передаётся Cross-Encoder для повторной оценки каждого кандидата. Запросы длиннее 500 токенов отклоняются.

### types

Определяет, какие типы фактов искать. Допустимые значения: `world` (объективные факты), `experience` (события и разговоры) и `observation` (обобщённые, подтверждённые данными выводы, полученные из нескольких воспоминаний). Если параметр не указан, ищутся все три типа.

Для каждого типа отдельно запускается полный конвейер из четырёх стратегий. Поэтому сужение `types` уменьшает количество результатов и стоимость запроса.

### Python

```python
# Только факты типа world (объективная информация)
world_facts = client.recall(
    bank_id="my-bank",
    query="Where does Alice work?",
    types=["world"]
)

# Только опыт (разговоры и события)
experience = client.recall(
    bank_id="my-bank",
    query="What have I recommended?",
    types=["experience"]
)

# Только наблюдения (обобщённые знания)
observations = client.recall(
    bank_id="my-bank",
    query="What patterns have I learned?",
    types=["observation"]
)
```

### Node.js

```javascript
await client.recall('my-bank', 'query', { types: ['world'] });
await client.recall('my-bank', 'query', { types: ['experience'] });
await client.recall('my-bank', 'query', { types: ['observation'] });
```

> **💡 Об наблюдениях**
>
> Наблюдения — это дедуплицированные выводы, основанные на фактах и объединённые из нескольких записей: предпочтения, повторяющиеся закономерности и долговременные знания, накопленные банком памяти. Каждое наблюдение содержит ссылки на подтверждающие воспоминания с точными цитатами и уточняется по мере появления данных, а не перезаписывается. Они автоматически создаются и обновляются в фоне после операций retain.

### prefer_observations

Наблюдения объединяют исходные факты. Поэтому при одновременном поиске `observation`, `world` и `experience` одна и та же информация может вернуться дважды: как исходный факт и как обобщённое наблюдение. Параметр `prefer_observations` помогает избежать дублей: ищутся все типы, но если наблюдение создано на основе найденного исходного факта, исходный факт исключается, а наблюдение его заменяет. Освободившиеся места заполняются следующими лучшими результатами — охват не уменьшается.

Так можно искать все сведения, не выбирая между «только исходные факты» (без обобщения) и «только наблюдения» (они могут отставать от новых данных, пока выполняется консолидация). **По умолчанию отключён** — задайте `true`, чтобы включить. Параметр действует только тогда, когда в `types` указаны `observation` и хотя бы один из типов `world` / `experience`.

### budget

Управляет глубиной и шириной поиска. Допустимы `low`, `mid` (по умолчанию) и `high`. Выберите `low` для простого и быстрого поиска, `mid` для повседневного баланса, `high` — для косвенных связей и исчерпывающего поиска.

```python
# Быстрый поиск
results = client.recall(bank_id="my-bank", query="Alice's email", budget="low")

# Глубокий поиск
results = client.recall(bank_id="my-bank", query="How are Alice and Bob connected?", budget="high")
```

### max_tokens

Максимальное суммарное количество токенов в возвращённых фактах. По умолчанию `4096`. Учитывается только поле `text`; метаданные, метки, сущности и другие поля не входят в лимит. После повторного ранжирования факты включаются по убыванию релевантности, пока лимит не будет исчерпан. Hindsight рассчитан на агентов, которые работают с токенами, а не количеством результатов. Установите `max_tokens`, чтобы определить, какую часть контекстного окна выделить для воспоминаний.

```python
# Заполнить подходящими воспоминаниями до 4 тысяч токенов контекста
results = client.recall(bank_id="my-bank", query="What do I know about Alice?", max_tokens=4096)

# Меньший лимит для быстрого поиска
results = client.recall(bank_id="my-bank", query="Alice's email", max_tokens=500)
```

### query_timestamp

Дата и время в формате ISO 8601, соответствующие моменту, когда пользователь задаёт запрос. Используется как точка отсчёта для относительных временных выражений и оценки давности. Например, если запрос содержит «в прошлом месяце», а `query_timestamp` равен `2023-05-30`, период поиска будет примерно соответствовать апрелю 2023 года, а давность оценивается на 30 мая 2023 года. Без параметра используется текущее время сервера. Особенно важен при воспроизведении старых разговоров и создании агентов, которым нужен поиск относительно заданного времени.

### include

Необязательный объект, задающий дополнительные данные, возвращаемые вместе с основными фактами.

#### chunks

Если включено, ответ содержит исходные текстовые фрагменты, из которых были извлечены факты. Фрагменты загружаются до фильтрации по `max_tokens`, поэтому при `max_tokens=0` факты не вернутся, но фрагменты могут присутствовать. Подпараметр `max_tokens` (по умолчанию `8192`) независимо задаёт общий лимит токенов фрагментов. Он полезен, когда агенту нужен более широкий контекст, чем текст извлечённого факта.

> **📝 Примечание**
>
> При включённом `include_chunks` фрагменты выбираются по результатам с наивысшими оценками Cross-Encoder до фильтрации по токенам. Последний фрагмент обрезается, а не удаляется, чтобы точно уложиться в лимит. У каждого фрагмента есть флаг `truncated`, показывающий, был ли текст обрезан.

#### source_facts

Если включено и в `types` есть `observation`, вместе с каждым наблюдением возвращаются исходные факты, из которых оно было синтезировано. Они представлены в словаре верхнего уровня `source_facts`, где ключ — идентификатор факта; результат-наблюдение содержит список `source_fact_ids` для перекрёстных ссылок. Факты дедуплицируются между наблюдениями. Подпараметр `max_tokens` (по умолчанию `4096`) задаёт общий лимит токенов исходных фактов.

### Python

```python
# Получить наблюдения вместе с исходными фактами
response = client.recall(
    bank_id="my-bank",
    query="What patterns have I learned about Alice?",
    types=["observation"],
    include_source_facts=True,
    max_source_facts_tokens=4096,
)

for obs in response.results:
    print(f"Observation: {obs.text}")
    if obs.source_fact_ids and response.source_facts:
        print("  Derived from:")
        for fact_id in obs.source_fact_ids:
            fact = response.source_facts.get(fact_id)
            if fact:
                print(f"    - [{fact.type}] {fact.text}")
```

#### entities

По умолчанию включено. Каждый возвращённый факт содержит канонические имена связанных с ним сущностей. Задайте `null`, чтобы пропустить JOIN-запрос к сущностям и уменьшить ответ. Подпараметр `max_tokens` (по умолчанию `500`) предназначен для будущего ограничения объёма данных о сущностях.

### tags

Ограничивает поиск воспоминаниями с указанными метками. Если параметр не задан, подходят воспоминания с любыми метками или без них. Фильтрация по меткам применяется на уровне базы данных во всех четырёх стратегиях, а не после получения результатов.

Параметр `tags_match` задаёт способ фильтрации:

| Режим | Воспоминания без меток | Условие совпадения |
|-------|-----------------------|--------------------|
| `any` (по умолчанию) | включаются | Воспоминание имеет **хотя бы одну** из указанных меток |
| `any_strict` | исключаются | Воспоминание имеет **хотя бы одну** из указанных меток |
| `all` | включаются | Воспоминание имеет **все** указанные метки |
| `all_strict` | исключаются | Воспоминание имеет **все** указанные метки |
| `exact` | исключаются | Набор меток воспоминания **точно совпадает** с указанным |

#### Пример исходных данных

Предположим, банк содержит четыре воспоминания:

| Воспоминание | Метки |
|--------------|-------|
| «Элис предпочитает асинхронное общение» | `["user:alice"]` |
| «Боб не любит долгие совещания» | `["user:bob"]` |
| «Команда использует Slack для объявлений» | `["user:alice", "team"]` |
| «Правило компании: по пятницам совещаний нет» | *(без меток)* |

#### `any` — совпадение ИЛИ, включая записи без меток (по умолчанию)

Возвращает воспоминания хотя бы с одной подходящей меткой и записи без меток.

```python
response = client.recall(
    bank_id="my-bank",
    query="communication preferences",
    tags=["user:alice"],
    tags_match="any",  # режим по умолчанию
)
# Возвращает:
#   [совпадение] "Alice prefers async communication"     — есть "user:alice"
#   [нет]        "Bob dislikes long meetings"             — нет общих меток с ["user:alice"]
#   [совпадение] "Team uses Slack for announcements"      — есть "user:alice"
#   [совпадение] "Company policy: no meetings on Fridays" — без меток, включено по умолчанию
```

Используйте этот режим для сочетания **общих сведений и сведений конкретного пользователя**, когда записи без меток должны быть доступны всем.

#### `any_strict` — совпадение ИЛИ, записи без меток исключаются

Работает как `any`, но исключает записи без меток. Используйте его, когда воспоминания **полностью разделены метками** и записи без меток не должны быть видны.

#### `all` — совпадение И, записи без меток включаются

Возвращает воспоминания со всеми указанными метками, а также записи без меток. Используйте, когда воспоминание должно принадлежать **пересечению заданных областей** (например, относиться и к пользователю, и к проекту), сохраняя доступ к общим сведениям.

#### `all_strict` — совпадение И, записи без меток исключаются

Возвращает воспоминания со всеми заданными метками и исключает записи без них. Используйте для строгого ограничения области, когда запись должна явно принадлежать **всем** указанным контекстам.

> **💡 Дополнительные метки допустимы**
>
> Воспоминание с метками `["user:alice", "team", "project:x"]` подходит фильтру `["user:alice", "team"]` в режиме `all_strict`: дополнительные метки не мешают совпадению. Фильтр требует, чтобы присутствовали **как минимум** перечисленные метки.

#### `exact` — точное совпадение набора, записи без меток исключаются

Возвращает воспоминания, набор меток которых точно совпадает с заданным, независимо от порядка. В отличие от `all_strict`, записи с дополнительными метками не подходят.

Используйте этот режим для точной области наблюдений из `GET /v1/default/banks/{bank_id}/observations/scopes`, если `["user:alice"]` не должно совпадать с наблюдениями с метками `["user:alice", "project:x"]`.

> **💡 Фильтр только для общих наблюдений без меток**
>
> Пустая область — полноценная область. В неё консолидация записывает результаты с `observation_scopes: "shared"`. Чтобы получить **только глобальные воспоминания без меток** и исключить все помеченные, задайте `tags_match: "exact"` и не передавайте метки (не указывайте `tags` или передайте `[]`):

```json
{ "query": "...", "tags": [], "tags_match": "exact" }
```

Для остальных режимов `tags_match` пустой или отсутствующий `tags` означает «не фильтровать по меткам». Только в режиме `exact` пустой список выбирает «общую область». Так можно получить только глобальные наблюдения после перехода к более конкретным областям.

### tag_groups

Список составных логических фильтров по меткам. Группы в списке объединяются оператором И на верхнем уровне. Каждая группа — рекурсивное логическое выражение: **листовой узел** `{tags, match}` или **составной узел** `{and: [...]}`, `{or: [...]}` либо `{not: ...}`.

Параметры `tag_groups` и `tags` / `tags_match` можно использовать вместе — они объединяются оператором И.

#### Листовой узел

```json
{ "tags": ["step:5", "step:8"], "match": "any_strict" }
```

`match` принимает те же значения, что и `tags_match`: `any`, `all`, `any_strict`, `all_strict`, `exact`. По умолчанию — `any_strict`.

#### Составные узлы

```json
{ "and": [ <TagGroup>, <TagGroup>, ... ] }
{ "or":  [ <TagGroup>, <TagGroup>, ... ] }
{ "not": <TagGroup> }
```

#### Примеры

**Фильтр этапов И область пользователя** — две группы верхнего уровня объединены И:

```json
{
  "tag_groups": [
    { "tags": ["step:5", "step:8", "step:12"], "match": "any_strict" },
    { "tags": ["user:ep_42"], "match": "all_strict" }
  ]
}
```

**Вложенное ИЛИ внутри И** — пользователь должен совпасть, а также должен совпасть этап или приоритет:

```json
{
  "tag_groups": [
    { "tags": ["user:alice"], "match": "all_strict" },
    { "or": [
        { "tags": ["step:5"], "match": "any_strict" },
        { "tags": ["priority:high"], "match": "all_strict" }
    ]}
  ]
}
```

**Исключение** — пользователь должен совпасть, но архивные воспоминания исключаются:

```json
{
  "tag_groups": [
    { "tags": ["user:alice"], "match": "all_strict" },
    { "not": { "tags": ["archived"], "match": "any_strict" } }
  ]
}
```

### trace

При значении `true` ответ содержит подробную диагностическую трассировку: вектор запроса, начальные узлы поиска, результаты каждой стратегии, кандидатов для объединения RRF, повторно ранжированные результаты, распознанные временные ограничения и длительность каждого этапа. На сам поиск параметр не влияет. Полезен, чтобы понять, почему конкретные воспоминания вернулись или не попали в ответ.

### min_scores

Необязательный объект, задающий минимальные баллы для отдельных этапов. Каждое значение сравнивается включительно (`>=`) с соответствующим полем [`scores`](#scores) и сочетается с другими условиями через И. Для неуказанных полей порога нет; если `min_scores` вообще не задан (по умолчанию), фильтрация по баллам отсутствует. Четыре поля относятся к **двум разным уровням конвейера**:

| Поле | Уровень | Действие |
|------|---------|----------|
| `semantic` | Поиск | Минимальное векторное сходство, применяемое в SQL: слабые совпадения удаляются **до** объединения. Переопределяет общий минимум сходства для этого запроса. |
| `keyword` | Поиск | Минимальный балл ключевого слова или полнотекстового поиска (BM25), применяемый в SQL: слабые результаты удаляются до объединения. |
| `reranker` | После запроса | Минимальный нормализованный балл Cross-Encoder для уже ранжированных результатов. |
| `final` | После запроса | Минимальный итоговый балл ранжирования для уже ранжированных результатов. |

```json
{ "query": "...", "min_scores": { "reranker": 0.5 } }
```

Пороги поиска (`semantic` / `keyword`) меняют **состав кандидатов** и поэтому могут изменить итоговый порядок. Пороги после запроса (`reranker` / `final`) удаляют только уже ранжированные результаты. Освободившиеся места **не заполняются** заново, поэтому при любом пороге результатов может оказаться меньше, чем позволяет budget.

**Используйте пороги осторожно.** Баллы повторного ранжирования надёжны для упорядочивания, но не являются *абсолютными*: явно релевантное воспоминание в одном запросе может получить около `0.001`, а в другом — около `1.0`. Фиксированный порог может незаметно отсеять хорошие результаты. Сначала выполните Recall без `min_scores` и изучите объект [`scores`](#scores), затем подберите порог по реальным значениям.

Порог сравнивается с тем же значением `score`, которое возвращается в ответе. Перед заданием фиксированного порога прочитайте пояснение к [`score`](#score): шкала относительная, а не абсолютная.

## Ответ

### results

Основной список извлечённых фактов, отсортированный по релевантности. Для расчёта одновременно запускаются четыре стратегии — семантическое сходство, BM25, обход графа и поиск по времени; их рейтинги объединяются Reciprocal Rank Fusion (RRF), затем объединённые кандидаты повторно оцениваются Cross-Encoder относительно исходного запроса.

У каждого результата есть объект [`scores`](#scores). Считайте его значения **относительными**: они отражают порядок в рамках одного запроса, а не абсолютную уверенность между разными запросами. Значение `0.8` в одном запросе нельзя напрямую сравнивать с `0.8` в другом. Обычно агенту лучше обрабатывать воспоминания по порядку и позволить `max_tokens` определить, сколько поместится, вместо фильтрации по баллу. Объекты `scores` и параметр [`min_scores`](#min_scores) нужны тем, кому важно изучать порядок или отбрасывать хвост результатов с низкой уверенностью. Порог подбирайте по баллам, полученным без фильтрации.

Каждый элемент `results` содержит поля:

- **`id`** — уникальный идентификатор факта. Используется для связи с `source_facts` или дедупликации на уровне приложения.
- **`text`** — текст факта, сохранённый в банке памяти.
- **`type`** — категория факта: `world` для объективных сведений, `experience` для событий и разговоров, `observation` для знаний, обобщённых со временем.
- **`context`** — метка контекста, заданная при сохранении (например, `"team meeting"`, `"slack"`); `null`, если не задана.
- **`metadata`** — пары строковых ключей и значений, добавленные при сохранении; `null`, если их нет.
- **`tags`** — метки видимости этого факта.
- **`entities`** — список канонических имён связанных сущностей. Заполняется, только если включено `include.entities` (по умолчанию); иначе `null`.
- **`occurred_start` / `occurred_end`** — даты и время начала и окончания события в формате ISO 8601. LLM извлекает их из содержимого во время retain; `null`, если сведений о времени нет.
- **`mentioned_at`** — дата и время сохранения факта в банке, ISO 8601.
- **`document_id`** — идентификатор документа, заданный при retain.
- **`chunk_id`** — идентификатор фрагмента исходного текста. Используется для ссылки на `chunks`, если включено `include.chunks`.
- **`source_fact_ids`** — только для результатов типа `observation`: идентификаторы исходных фактов, из которых синтезировано наблюдение. Ссылки на `source_facts`; для других типов или если `include.source_facts` отключён, имеет значение `null`.
- **`scores`** — баллы отдельных этапов. У записей `source_facts`, добавленных по происхождению, значение `null`. Поля:
  - **`final`** — балл ранжирования факта: релевантность Cross-Encoder, умноженная на поправки давности, времени и подтверждений. `results` отсортированы по убыванию. Это относительный показатель, а не откалиброванная вероятность.
  - **`reranker`** — нормализованная релевантность Cross-Encoder (`0`–`1`); `null` для развёртывания с режимом пропуска Cross-Encoder (RRF или interleave).
  - **`semantic`** — исходное косинусное сходство векторов (`0`–`1`); `null`, если результат не найден семантическим поиском.
  - **`keyword`** — исходный балл полнотекстового поиска BM25 (`≥ 0`, верхней границы нет); `null`, если результат не найден поиском по ключевым словам.

Каждое поле баллов также можно использовать как порог в [`min_scores`](#min_scores).

### source_facts

Словарь по идентификаторам фактов, содержащий полные объекты `RecallResult` для исходных фактов, которые участвовали в создании наблюдений. Возвращается, только если включено `include.source_facts`. Факты дедуплицируются: если на один исходный факт ссылаются два наблюдения, он возвращается один раз.

### chunks

Словарь по идентификаторам фрагментов, содержащий исходные текстовые фрагменты для возвращённых фактов. Присутствует, только если включено `include.chunks`. У каждого фрагмента есть поля `id`, `text`, `chunk_index` и `truncated` (показывает, обрезан ли текст для соблюдения лимита токенов).

### entities

Словарь по каноническим именам сущностей, содержащий объекты состояния сущностей. Присутствует, только если включено `include.entities`. Записи содержат `entity_id`, `canonical_name` и `observations`.

### trace

Диагностический объект, возвращаемый только при `trace: true` в запросе. Содержит длительность этапов, состав результатов поиска и сведения об объединении RRF.

# Быстродействие

Hindsight рассчитан на быстрые операции смысловой памяти при большой нагрузке. Здесь описаны скорость, способы ускорения и правила работы.

## Обзор

В Hindsight ускорены три главные операции:

- **Retain (загрузка)**: пакетная обработка и асинхронный режим для записи больших объёмов памяти.
- **Recall (поиск)**: смысловой поиск быстрее секунды с настраиваемым бюджетом рассуждения.
- **Reflect (вывод)**: создание ответа с учётом черт поведения и настраиваемыми затратами вычислений.

## Основной принцип: быстрый поиск

Hindsight **изначально устроен так, чтобы чтение было быстрее записи**. Память обычно записывают один раз, а читают много раз.

Поэтому система тратит больше времени при записи, чтобы **recall занимал меньше секунды**:

- **Векторы создаются заранее**: при сохранении воспоминаний векторы уже строятся и попадают в индекс.
- **Быстрый поиск по векторам**: индексы HNSW ускоряют поиск близких соседей с допустимой погрешностью.
- **Извлечение фактов при записи**: сложная работа LLM идёт во время retain, а не при поиске.
- **Структурные графы памяти**: связи и сведения о времени определяются заранее.

Поэтому **Recall работает быстро**: трудная часть уже сделана.

### Сравнение скорости

| Операция | Обычная задержка | Главное узкое место | Способ ускорить |
|-----------|----------------|-------------------|----------------------------------|
| **Recall** | 100–600 мс | Модель повторной сортировки на CPU | Перенести её на GPU или снизить бюджет |
| **Reflect** | 800–3000 мс | Создание текста LLM | Взять более быструю LLM |
| **Retain** | 500–2000 мс на пакет | **Извлечение фактов LLM** | Взять поставщика LLM с высокой пропускной способностью |

Цель — держать **чтение в приложении (recall/reflect) быстрым**, даже если запись займёт больше времени. Это верный выбор для памяти, когда:

- Воспоминания пишутся в фоне или при малой нагрузке.
- К памяти часто обращаются в действиях пользователя, где важна задержка.
- Чтений больше, чем записей: обычно не менее 10 к 1.

## Скорость Retain

**Retain по природе медленнее**, потому что LLM извлекает факты, находит сущности, учитывает время, строит связи и создаёт векторы. **Главное узкое место записи — LLM**.

### Hindsight не нужна самая сильная модель

Извлечение фактов — чёткая задача, поэтому небольшие быстрые модели справляются хорошо. Мы советуем `gpt-oss-20b` (доступна через Groq и других поставщиков).

Чтобы писать быстрее:

1. **Берите поставщика LLM с высокой пропускной способностью**: с большим лимитом запросов в минуту (RPM) и малой задержкой.
   - **Быстро**: [Groq](https://groq.com) с `gpt-oss-20b` или другими моделями openai-oss; свои модели на узлах с GPU (vLLM, TGI).
   - **Медленно**: облачные LLM с низкими лимитами запросов.

2. **Объединяйте операции в пакеты**: передавайте связанный текст одним запросом. В одном запросе можно отправить сколько угодно данных; предел задаёт лишь размер тела HTTP.

3. **Для больших наборов берите асинхронный режим**: ставьте задачи в очередь.

4. **Обрабатывайте параллельно**: для очень больших наборов запустите несколько вызовов retain одновременно с разными `document_id`.

### Автоматическая настройка пакетов

**При асинхронном retain Hindsight сам выбирает размер пакетов.** Вам не нужно вручную подбирать его или делить текст на части.

Как это работает:
- **Отправка больших пакетов**: сотни или тысячи элементов в одном асинхронном запросе retain.
- **Автоматическая разбивка**: пакеты крупнее 10 000 токенов делятся на удобные части.
- **Параллельная обработка**: части идут в фоне одновременно.
- **Слежение за ходом**: главная операция собирает статусы всех частей.
- **Подсчёт по токенам**: для размера пакета применяется tiktoken, а не число символов.

Польза:
- Целый документ или набор данных уходит одним вызовом API.
- Способ обработки подбирает Hindsight.
- За общим ходом можно следить по статусу главной операции.
- Не нужно самим дробить данные на мелкие пакеты.

### Пропускная способность

На неё влияют:
- Размер и сложность документов.
- Лимиты запросов поставщика LLM при извлечении фактов.
- Скорость записи в базу.
- Свободные ресурсы CPU и памяти.

## Настройка для местных и малых сред

Настройки по умолчанию рассчитаны на облачные LLM и серверы с несколькими ядрами. На ноутбуке, одном узле с GPU или **местном сервере LLM** (llama.cpp, vLLM, LM Studio, Ollama) с малым числом мест они могут забить сервер, вызвать тайм-ауты или перегрузить CPU. Здесь собраны важные настройки для слабой машины.

### Число одновременных вызовов LLM

Значение по умолчанию `HINDSIGHT_API_LLM_MAX_CONCURRENT=32` рассчитано на облако, способное принять десятки запросов разом. У местного сервера может быть всего несколько мест. Тогда Hindsight займёт их все и **не оставит места другим клиентам того же адреса**: вашему главному агенту, другому приложению или второй операции Hindsight.

```bash
export HINDSIGHT_API_LLM_MAX_CONCURRENT=2
```

Значение `2` позволяет retain и обобщению идти вместе, не блокируя друг друга. Если адрес **общий** для других приложений, агентов или цепочек на том же llama-server / vLLM / LM Studio, снизьте предел ещё: оставьте хотя бы одно место на каждого другого клиента.

Можно также задать пределы по операциям, чтобы фоновая работа не мешала живым запросам. Эти пределы действуют *поверх* общего:

```bash
# global=4, with retain/consolidation capped low so reflect always has headroom
export HINDSIGHT_API_LLM_MAX_CONCURRENT=4
export HINDSIGHT_API_RETAIN_LLM_MAX_CONCURRENT=1
export HINDSIGHT_API_CONSOLIDATION_LLM_MAX_CONCURRENT=1
```

### Время ожидания и повторы

Небольшие модели на слабой машине создают токены медленно, а первый запрос после запуска ещё и ждёт загрузки модели. Значение по умолчанию `HINDSIGHT_API_LLM_TIMEOUT=120` секунд может быть слишком малым для крупной местной модели на CPU. Поднимите его, чтобы избежать ложных тайм-аутов и лишних повторов:

```bash
export HINDSIGHT_API_LLM_TIMEOUT=300        # allow slow local generation
export HINDSIGHT_API_LLM_MAX_RETRIES=2      # fail faster locally — retries rarely help a slow box
```

У местного адреса нет лимита частоты запросов, поэтому частые повторы с растущими паузами при настоящей ошибке лишь тратят время. Снизьте число повторов, чтобы ошибки появлялись быстрее.

### Меньшие и более быстрые модели, бюджет рассуждения

Retain извлекает факты по чётким правилам и не требует передовой модели. Для reflect можно взять ещё более лёгкую. На слабой машине каждой операции дайте самую малую модель, которая справляется:

```bash
# Reflect on a small/fast model; retain on a slightly stronger structured-output model
export HINDSIGHT_API_REFLECT_LLM_MODEL=<small-fast-model>
export HINDSIGHT_API_RETAIN_LLM_MODEL=<structured-output-model>
```

Если модель позволяет задавать бюджет рассуждения, оставьте его низким (значение по умолчанию). Лишние токены рассуждения лишь замедляют извлечение и обобщение:

```bash
export HINDSIGHT_API_LLM_REASONING_EFFORT=low
```

При обобщении несколько фактов идут в LLM одним вызовом (по умолчанию 8). Для малой модели с коротким окном контекста крупный пакет даёт слишком длинный запрос и ответ, в котором легко ошибиться. Снизьте размер, чтобы вызовы были короткими и надёжными:

```bash
export HINDSIGHT_API_CONSOLIDATION_LLM_BATCH_SIZE=2   # default 8; lower = smaller prompts, more calls
```

### Настройка встроенного llama.cpp

Встроенный поставщик `llamacpp` запускает сервер llama.cpp как управляемый дочерний процесс; отдельный сервер не нужен. Важные настройки для малых машин:

```bash
export HINDSIGHT_API_LLM_PROVIDER=llamacpp
export HINDSIGHT_API_LLM_MAX_CONCURRENT=2        # retain + consolidation without blocking
export HINDSIGHT_API_LLAMACPP_GPU_LAYERS=-1      # -1 = offload all layers to GPU; 0 = CPU only
export HINDSIGHT_API_LLAMACPP_CONTEXT_SIZE=8192  # lower to save RAM/VRAM; raise for big batches
export HINDSIGHT_API_LLAMACPP_EXTRA_ARGS="--n_threads 8"  # match physical cores on CPU-only boxes
# export HINDSIGHT_API_LLAMACPP_NO_GRAMMAR=true  # faster, but less reliable JSON output
```

Полный список есть в разделе [«Встроенный llama.cpp»](./configuration#built-in-llamacpp).

### Повторная сортировка на CPU

На машине без GPU главное узкое место recall — кросс-энкодер, который повторно сортирует результаты. Для местной модели есть настройки CPU и Apple Silicon: они заметно ускоряют работу без потери качества.

```bash
# Apple Silicon (MPS): half precision is 27–36% faster, quality-identical
export HINDSIGHT_API_RERANKER_LOCAL_FP16=true

# Sort pairs by length before batching — 36–54% faster, quality-identical by construction
export HINDSIGHT_API_RERANKER_LOCAL_BUCKET_BATCHING=true

# Cap reranker parallelism so it doesn't thrash a small CPU under load (default 4)
export HINDSIGHT_API_RERANKER_LOCAL_MAX_CONCURRENT=2

# On macOS, force CPU if MPS/XPC causes instability
# export HINDSIGHT_API_RERANKER_LOCAL_FORCE_CPU=true
```

Самый сильный способ ускорить CPU — сортировать меньше кандидатов. По умолчанию Hindsight передаёт в этот шаг до 300 кандидатов за один recall. Сократите число, чтобы пропорционально снизить работу кросс-энкодера:

```bash
export HINDSIGHT_API_RERANKER_MAX_CANDIDATES=100   # default 300; RRF pre-filters the rest
```

Для машины только с CPU, где кросс-энкодер слишком тяжёл, можно взять более лёгкую модель `flashrank` на ONNX:

```bash
export HINDSIGHT_API_RERANKER_PROVIDER=flashrank
```

Можно снизить и сам объём работы recall: для будничных запросов берите меньший `budget` (`low`/`mid`), а `high` оставьте для глубокого вывода. См. ниже [«Скорость Recall»](#recall-performance).

## Скорость Recall

### Бюджет

Параметр `budget` задаёт глубину и качество поиска. Выбирайте по сложности вопроса: для полного разбора нужен более высокий бюджет.

| Бюджет | Задача |
|--------|----------|
| `low` | Быстрый поиск, живой чат |
| `mid` | Обычный вопрос, баланс скорости и качества |
| `high` | Широкий вопрос и глубокий разбор |

### Как ускорить

1. **Подходящий бюджет**: простой вопрос — малый, глубокий вывод — высокий.
2. **Лимит токенов ответа**: `max_tokens` задаёт размер ответа (по умолчанию 4096).
3. **Исходные фрагменты**: включите `include_chunks`, если нужен точный текст, из которого получены воспоминания.

### Скорость базы

Hindsight берёт PostgreSQL с pgvector для поиска по векторам:

- **Вид индекса**: HNSW для быстрого поиска близких соседей.
- **Обычная задержка**: 10–50 мс для поиска по векторам среди более 100 тысяч фактов.
- **Масштаб**: проверена работа с миллионами фактов на банк.

## Скорость Reflect

### Из чего складывается задержка

| Часть | Задержка | Описание |
|-----------|----------------|-------------|
| Поиск памяти | 100–600 мс | Зависит от бюджета (`low`/`mid`/`high`) |
| Создание ответа LLM | 500–2000 мс | Зависит от поставщика и длины ответа |
| **Всего** | **600–2600 мс** | Обычная задержка от начала до конца |

### Как ускорить

1. **Выбор бюджета**: снижайте его, если контекста уже хватает.
2. **Передача контекста**: задавайте нужный `context`, чтобы не тратить время на широкий поиск и получить более точный ответ.

## Советы по работе

### Операции
- **Подбирайте бюджет**: не тратьте высокий бюджет на простой вопрос; оставляйте его для глубокого вывода.
- **Пишите пакетами**: объединяйте связанный текст для более быстрой работы.
- **Кешируйте частые запросы**: если запросы повторяются, храните ответы на стороне приложения.
- **Измеряйте через trace**: параметр `trace` помогает найти медленные шаги.

### Масштабирование
- **Несколько экземпляров**: запустите несколько API за балансировщиком с общей базой PostgreSQL.
- **Одновременные запросы**: поддерживается более 100 запросов; скорость поиска памяти растёт с числом ядер CPU.
- **Лимиты LLM**: распределяйте запросы между ключами и поставщиками (обычно 60–500 запросов в минуту на ключ).

### Снижение затрат
- **Лёгкие модели**: для retain берите `gpt-oss-20b` через Groq; Hindsight не требует передовых моделей.
- **Пакетный API поставщика**: задайте `HINDSIGHT_API_RETAIN_BATCH_ENABLED=true` вместе с асинхронным retain. Это снижает цену извлечения фактов LLM на 50% (поддерживают OpenAI и Groq; результат приходит в течение 24 часов).
- **Лимиты токенов**: ограничьте `max_tokens` для recall и снижайте бюджет, когда можно.
- **Размер частей**: крупные части по 1000–2000 токенов выгоднее множества мелких.

### Слежение за работой
- **Метрики Prometheus**: доступны на `/metrics`; смотрите задержки по долям, пропускную способность и число ошибок.
- **Главные метрики**: `hindsight_recall_duration_seconds`, `hindsight_reflect_duration_seconds`, `hindsight_retain_items_total`.

# Диагностика стабильности в Compose

## Главный принцип

Исправляй параметры Compose на основе фактов. Сначала выясни режим компилятора и способ сравнения параметров, затем меняй модель или место вызова, которое на деле мешает пропускать рекомпозицию.

Начиная с Kotlin 2.0.20, strong skipping включён по умолчанию. Нестабильные параметры больше не делают перезапускаемый composable автоматически непригодным для пропуска. Но нестабильные параметры сравниваются по тождеству экземпляра (`===`), а стабильные — через `equals`. Частое создание новых нестабильных экземпляров всё ещё мешает пропуску.

## Порядок диагностики

1. Подтверди симптом: число рекомпозиций, данные отчёта компилятора или частое создание подозрительного параметра.
2. Узнай режим компилятора: версии Kotlin и Compose Compiler, включён ли strong skipping.
3. Создай или прочитай отчёты Compose Compiler для варианта сборки, который выпускается пользователям.
4. Для каждого подозрительного параметра выясни причину: правила стабильности, смена экземпляров или лямбда/вычисленное значение, созданное вызывающим кодом.
5. Примени наименьшую правку, которая честно описывает тип или место вызова.
6. Повтори измерение на том же действии или перечитай тот же отчёт, прежде чем считать проблему решённой.

## 1. Сначала разбери strong skipping

В Kotlin 2.0.20+ этот режим включён по умолчанию:

- Перезапускаемые composable можно пропускать даже при нестабильных параметрах, если это явно не отключено.
- Стабильные параметры сравниваются через `equals`.
- Нестабильные параметры сравниваются по тождеству экземпляра (`===`).
- Лямбды внутри composable автоматически запоминаются с учётом захваченных значений.

Спроси себя: «Параметры будут сравниваться так, как я ожидаю? Не создаёт ли вызывающий код новые нестабильные экземпляры на каждом кадре?»

На старых версиях компилятора или при выключенном strong skipping действует прежнее правило: composable с нестабильными параметрами может перезапускаться, но не пропускаться.

## 2. Создай отчёты компилятора

В Kotlin 2.0+ Compose Compiler настраивается через плагин Kotlin Gradle:

```kotlin
plugins {
    alias(libs.plugins.android.application) // or android.library / jvm
    alias(libs.plugins.kotlin.android)      // or kotlin.multiplatform / kotlin.jvm
    alias(libs.plugins.compose.compiler)
}

if (providers.gradleProperty("composeReports").orNull == "true") {
    composeCompiler {
        reportsDestination = layout.buildDirectory.dir("compose_compiler")
        metricsDestination = layout.buildDirectory.dir("compose_compiler")
    }
}
```

Затем собери нужный вариант, например:

```bash
./gradlew :app:assembleRelease -PcomposeReports=true
```

Для оценки скорости работы бери release-сборку без отладки. Отчёты создаются при сборке, поэтому их вариант и флаги компилятора должны совпадать с теми, что идут в выпуск.

Главные файлы:

| Файл | Что показывает |
|---|---|
| `<module>-classes.txt` | Стабильность классов и свойств |
| `<module>-composables.txt` | Возможность перезапуска и пропуска, стабильность параметров |
| `<module>-composables.csv` | Те же данные в удобном для сортировки виде |
| `<module>-module.json` | Сводные метрики |

## 3. Исправляй лишь доказанную проблему с параметром

Выбирай самую лёгкую правку, которая делает обещания типа о неизменяемости или равенстве правдивыми.

### Неизменяемые коллекции

Если в отчёте видны интерфейсы коллекций в состоянии UI, на его границе предпочитай `kotlinx.collections.immutable`:

```kotlin
// До: нестабильные интерфейсы коллекций
data class UiState(val items: List<Item>, val tags: Set<String>)

// После: контракты неизменяемых коллекций
import kotlinx.collections.immutable.ImmutableList
import kotlinx.collections.immutable.ImmutableSet

data class UiState(val items: ImmutableList<Item>, val tags: ImmutableSet<String>)
```

Создающий код один раз преобразует коллекции на границе через `.toImmutableList()` / `.toImmutableSet()`.

### `@Immutable` / `@Stable`

- Применяй `@Immutable`, когда все свойства фактически неизменяемы, а равенство описывает всё видимое состояние.
- Применяй `@Stable` для типов, чьё изменяемое состояние наблюдается Compose, обычно через `MutableState`.

Не ставь аннотацию лишь ради чистого отчёта. Ложное обещание стабильности может оставить на экране устаревшие данные.

### Неизменяемые типы сторонних библиотек

Для типов, которые нельзя аннотировать, но можно честно считать неизменяемыми, используй `stabilityConfigurationFiles`:

```kotlin
composeCompiler {
    stabilityConfigurationFiles.add(
        rootProject.layout.projectDirectory.file("compose_stability.conf"),
    )
}
```

```text
java.math.BigDecimal
java.math.BigInteger
java.time.*
kotlinx.datetime.*
```

Вноси лишь типы, неизменяемость которых готов гарантировать. Не добавляй изменяемые типы вроде `java.util.Date`.

## 4. Стабилизируй входные значения элементов списка

Если элементы lazy-списка лишний раз пересобираются из-за новых значений при вызове, стабилизируй входы каждого элемента вместо слепого добавления аннотаций к моделям.

Подними и запомни значения, которые не меняются в течение жизни элемента:

```kotlin
// ❌ ПЛОХО — при рекомпозиции родителя создаются новые лямбды
items(list, key = { it.id }) { item ->
    RowCard(
        onClick = { onItemClick(item.id) },
        isHighlighted = { item.id == selectedId },
    )
}

// ✅ ХОРОШО — захваченные значения стабильны для этого элемента
items(list, key = { it.id }) { item ->
    val onClick = remember(item.id) { { onItemClick(item.id) } }
    val isHighlighted = remember(item.id, selectedId) { item.id == selectedId }
    RowCard(onClick = onClick, isHighlighted = isHighlighted)
}
```

Так же вынеси данные о месте строки (`isFirst`, `isLast`, радиусы углов) в `remember(index) { … }`, если они зависят только от индекса. Но не жди, что это само исправит запись состояния назад в фазу или чтение размеров соседних строк.

После подъёма проверь перемещение фокуса и вставку элементов тестами числа рекомпозиций.

## Краткая памятка

| Симптом | Причина | Исправление |
|---|---|---|
| Kotlin 2.0.20+, а старые документы называют нестабильный параметр непропускаемым | Strong skipping изменил поведение по умолчанию | Проверь правила сравнения и частоту создания экземпляров |
| `unstable val items: List<Item>` | Интерфейс коллекции | Примени `ImmutableList<Item>` или другую подлинно неизменяемую обёртку |
| `unstable val price: BigDecimal` | Внешний неизменяемый тип | Добавь его в конфиг стабильности |
| `@Immutable` у типа с изменяемыми внутренними полями | Ложное обещание | Исправь модель или убери аннотацию |
| Composable плохо пропускается и со strong skipping | Каждый раз создаётся новый нестабильный экземпляр | Запоминай, поднимай или сделай тип стабильным с сравнением по равенству |
| Элементы списка пересобираются вместе с родителем при тех же данных | Каждый раз новая лямбда или вычисленное значение | Запоминай для каждого элемента через `remember(item.id) { … }` |
| Отчётов нет | Нет плагина Compose Compiler или флага | Подключи `org.jetbrains.kotlin.plugin.compose` и укажи папки вывода |

## Когда не применять

- Проблема связана с записью состояния назад в фазу или чтением размеров соседних строк — смотри [`compose-state-deferred-reads`](../compose-state-deferred-reads/SKILL.md).
- Состояние прокрутки или анимации читается в композиции на каждом кадре — смотри тот же навык.
- Число рекомпозиций соответствует реальным изменениям данных.
- Ошибка вызвана неверными или устаревшими данными, а не лишней работой.
- Код используется только в тестах, где читаемость важнее чистоты отчёта.

## Связанные навыки

- [`compose-state-deferred-reads`](../compose-state-deferred-reads/SKILL.md) — состояние, меняющееся на каждом кадре, часто лучше читать во время layout/draw, а не композиции.
- [`compose-recomposition-performance`](../compose-recomposition-performance/SKILL.md) — начальная точка, если непонятно, какая причина рекомпозиции играет роль.

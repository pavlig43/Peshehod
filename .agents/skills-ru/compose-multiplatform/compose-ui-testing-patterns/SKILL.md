# Compose: шаблоны UI-тестов

## Главный принцип

Проверяй самый малый контракт UI, который доказывает нужное поведение. Предпочитай тесты простого UI с состоянием и callback-функциями. Подключай интеграцию, только когда проверяешь сам жизненный цикл, навигацию, DI или поведение платформы.

## Выбор теста

| Что нужно доказать | Вид теста |
|---|---|
| Текст, кнопка, ветка загрузки/ошибки, условный контент | Тест простого Compose UI |
| Вызов callback после нажатия или ввода | Тест простого Compose UI |
| Переход фокуса или работа клавиатуры | Compose-тест с вводом клавиш |
| Макет, обрезка, высота, шрифт, расположение картинок | Тест снимка экрана |
| State holder верно обновляет UI | Модульный тест state holder и один простой тест связки |
| Hover, нажатие, фокус, перетаскивание | Тест простого UI с `MutableInteractionSource` |
| Навигация, жизненный цикл, связка DI | Интеграционный тест |

## Предпочитай тесты простого UI

Если экран разделён на state holder и UI, тестируй сам UI-composable:

```kotlin
composeTestRule.setContent {
    ProfileScreen(
        state = ProfileUiState(name = "Ada", canSave = true),
        onNameChange = {},
        onSaveClick = { saved = true },
        onBackClick = {},
    )
}

composeTestRule.onNodeWithText("Ada").assertIsDisplayed()
composeTestRule.onNodeWithText("Save").performClick()

assertThat(saved).isTrue()
```

Так не нужно создавать ViewModel, компоненты, репозитории, навигацию и граф зависимостей ради проверки layout.

## Сначала semantics

Если поведение имеет семантический смысл, проверяй semantics:

- текст есть: `onNodeWithText`;
- кнопка доступна/недоступна: `assertIsEnabled`, `assertIsNotEnabled`;
- элемент выбран, в фокусе или переключён: соответствующие проверки semantics;
- элемента нет: `assertDoesNotExist`.

Теги нужны для узлов без устойчивого видимого текста или когда текст совпадает у нескольких узлов. Не начинай любую проверку с тегов: видимый пользователю смысл обычно даёт более надёжный тест.

## Проверка callback-функций

Используй простые счётчики или записанные значения:

```kotlin
var selectedId: String? = null

composeTestRule.setContent {
    ItemList(
        items = listOf(ItemUi("movie-1", "Movie")),
        onItemClick = { selectedId = it },
    )
}

composeTestRule.onNodeWithText("Movie").performClick()

assertThat(selectedId).isEqualTo("movie-1")
```

Для обычного значения, записанного callback-функцией, достаточно прямой проверки после действия. Применяй `runOnIdle`, если перед чтением результата Compose должен успеть применить snapshot-состояние, выполнить рекомпозицию или работу в очереди UI.

## Состояние взаимодействия через MutableInteractionSource

Если вид или работа composable зависит от наведения, фокуса, нажатия или перетаскивания, передай `MutableInteractionSource` и прямо отправь нужное состояние. Не имитируй мышь или касание ради этих состояний: такой тест хрупок, зависит от среды и часто нестабилен.

```kotlin
val interactionSource = MutableInteractionSource()

composeTestRule.setContent {
    OutlinedButton(
        onClick = {},
        interactionSource = interactionSource,
    )
}

// Проверка исходного состояния без наведения
composeTestRule.onNodeWithText("OutlinedButton").assertIsDisplayed()

// emit — suspend-функция, вызываем её из coroutine теста
TestScope().launch {
    interactionSource.emit(HoverInteraction.Enter())
}

composeTestRule.waitForIdle()

// Проверка видимого или семантического результата наведения
// (например, цвета рамки, высоты или снимка экрана)
composeTestRule.onNodeWithText("OutlinedButton").assertIsDisplayed()
```

Тот же шаблон работает для `PressInteraction.Press` / `Release` / `Cancel`, `FocusInteraction.Focus` / `Unfocus` и `DragInteraction.Start` / `Stop` / `Cancel`. Отправь входное событие, вызови `waitForIdle`, затем проверь результат.

Главное:

- **Всегда передавай `MutableInteractionSource`**, а не полагайся на внутренний источник: так переходы состояния полностью под контролем теста.
- **Отправляй события из coroutine scope**, например `TestScope().launch { }`, ведь `emit` — suspend-функция. `LaunchedEffect` относится к рабочему Compose-коду, это не инструмент теста.
- **Проверяй результат взаимодействия** — внешний вид, semantics или доступность, — а не само событие. Источник событий приводит тест в нужное состояние.
- **Используй этот подход и для снимков экрана**: отправь событие и снимай экран в известном состоянии.

## Клавиатура и фокус

Для клавиатуры, TV и Desktop запускай переходы тем же вводом, что использует человек: клавишами или D-pad. Одних нажатий мышью мало. Проверяй semantics фокуса, а не цвет или масштаб; снимки экрана оставь для вида подсветки.

Граф фокуса, `FocusRequester`, возврат фокуса, обработчики клавиш и шаблоны тестов описаны в [`compose-focus-navigation`](../compose-focus-navigation/SKILL.md).

## Тесты снимков экрана

Снимки нужны для видимых свойств, которые semantics не доказывает:

- отступы и выравнивание;
- цвета темы, шрифты, высота и тени;
- компоновка картинок, градиенты и наложения;
- вид подсветки фокуса;
- скелеты загрузки и насыщенные состояния UI.

Сделай состояние снимка воспроизводимым:

- используй фиксированные данные;
- по возможности останови часы или ход анимации;
- подмени сеть и загрузку картинок тестовым обработчиком;
- не проверяй меняющийся текст вроде текущего времени, если время не задано тестом.

## Подмена картинок и сервисов платформы

Когда содержимое картинки не важно, подмени загрузчик и проверь запрошенную модель, если проверяется именно она. Способ подмены зависит от библиотеки; помощник проекта может выглядеть так:

```kotlin
val requestedModels = mutableListOf<Any?>()

// Пример помощника, а не API Compose.
setContentWithFakeImageLoader { request ->
    requestedModels += request.data
    errorPainter()
}
```

Если важен вид картинки, дай локальный painter или bitmap с предсказуемым результатом вместо данных из сети.

## Частые ошибки

| Ошибка | Исправление |
|---|---|
| Создавать весь граф приложения ради проверки строки ошибки | Тестируй простой UI с `state = Error` |
| Проверять нажатие через mock ViewModel | Передай callback и проверь его вызов |
| Снимать экран ради наличия текста | Проверь semantics |
| Проверять отступ, цвет или кольцо фокуса через semantics | Примени снимок экрана |
| Ставить теги везде | Предпочитай текст, описание или роль, если они устойчивы |
| Зависеть от реальной сети, картинок или времени | Подмени или зафиксируй источник |
| Имитировать наведение, нажатие и фокус мышью или касанием | Передай `MutableInteractionSource` и отправь событие |
| Полагаться на источник взаимодействия по умолчанию | Передай управляемый `MutableInteractionSource` |
| Проверять TV/клавиатуру лишь через `performClick` | Используй ввод клавиш и проверку фокуса; смотри [compose-focus-navigation](../compose-focus-navigation/SKILL.md) |

## Тревожные признаки при проверке

- «Этот UI-тест иногда падает, потому что картинки загружаются медленно».
- Тест простого рендера поднимает рабочий DI.
- На снимке случайные даты, часы, картинки из сети или живые данные.
- После действия проверяют лишь существование узла, а не вызов callback или смену состояния.
- Фокус оценивают только на глаз, без проверки.
- Вместо `MutableInteractionSource.emit` тест применяет `performMouseInput` или касание для hover/press.
- Composable принимает `interactionSource`, но тест не передаёт `MutableInteractionSource`.

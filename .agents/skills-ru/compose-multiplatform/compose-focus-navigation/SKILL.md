# Compose: переходы фокуса

## Главное правило

Фокус — поведение интерфейса с состоянием. Явно выбирайте элементы, которые могут принять фокус; запрашивайте его после успешной композиции; проверяйте переходы тем же способом, каким пользуются люди: с клавиатуры, крестовины или пульта.

## Когда нужен этот навык

Берите его, если интерфейс:

- Работает на телевизоре, компьютере, ChromeOS, Android с клавиатурой или устройстве с пультом.
- Использует `FocusRequester`, `focusRequester`, `focusProperties`, `onFocusChanged` или обработчики клавиш.
- Нуждается в начальном или восстановленном фокусе, переходе по направлениям либо обработке «Назад» и Escape.
- Содержит карусель, сетку, ленивый список, меню, диалог или окно, где фокус может застрять.
- Проверяется тестами на фокус конкретного элемента.

## Создавайте цели фокуса осознанно

Начинайте с элементов, которые уже умеют получать фокус, и добавляйте лишь нужное для поведения:

| Задача | Что добавить |
|---|---|
| Фокус обычной кнопки, поля ввода или нажимаемого элемента | Ничего сверх самого элемента |
| Начальный или восстановленный фокус по команде | `FocusRequester` и `Modifier.focusRequester(...)` |
| Отклик вида или состояния на смену фокуса | `Modifier.onFocusChanged { ... }` |
| Своя нажимаемая поверхность, которая пока не получает фокус | `Modifier.focusable()` и нужную роль или семантику |

Например, запрашивайте и отслеживайте фокус вместе, лишь если нужны оба действия:

```kotlin
val requester = remember { FocusRequester() }

Button(
    onClick = onClick,
    modifier = Modifier
        .focusRequester(requester)
        .onFocusChanged { state -> isFocused = state.isFocused },
) {
    Text("Играть")
}
```

Предпочитайте готовые элементы с фокусом (`Button`, `TextField`, нажимаемые и выбираемые поверхности) ручному добавлению `focusable()` к пассивной разметке. Добавляйте его вручную, только если элемент и правда участвует в действии или переходах.

## Запрашивайте фокус после композиции

Вызывайте запрос фокуса из эффекта, а не из тела composable-функции:

```kotlin
val initialFocus = remember { FocusRequester() }

LaunchedEffect(initialFocus) {
    initialFocus.requestFocus()
}
```

Если цель появляется после загрузки, привяжите запрос к этому условию:

```kotlin
LaunchedEffect(items.isNotEmpty()) {
    if (items.isNotEmpty()) {
        firstItemRequester.requestFocus()
    }
}
```

В ленивом списке просите фокус, лишь когда элемент уже создан композицией. Держите запрос фокуса в стабильном состоянии элемента по его ID, а не только по номеру строки, если порядок может меняться.

## Переходы по направлениям

Берите `focusProperties`, если обычный поиск по положению на экране даёт неверный результат:

```kotlin
Modifier.focusProperties {
    up = headerRequester
    down = firstRowRequester
    left = FocusRequester.Cancel
}
```

Делайте это умеренно. Множество жёстких связей устареет при смене разметки. Оставляйте естественный порядок, если дизайн не требует особого перехода или ограничения фокуса.

## Нажатия клавиш

Обрабатывайте клавиши вручную для действий, которые не являются обычным нажатием или переходом фокуса:

```kotlin
Modifier.onPreviewKeyEvent { event ->
    if (event.type == KeyEventType.KeyUp && event.key == Key.Back) {
        onBack()
        true
    } else {
        false
    }
}
```

Возвращайте `true` только для обработанной клавиши. Слишком широкий ответ `true` ломает ввод текста, сочетания для доступности и переходы родителя.

При быстром вводе с крестовины ограничивайте частоту на границе дорогого действия, например прокрутки ряда или листания страниц, а не сразу на всём экране.

## Восстановление фокуса

Сохраняйте фокус по смысловому ID:

- Запоминайте ID выбранного элемента и элемента с фокусом, а не только индекс.
- Задавайте постоянные `key` в ленивых списках и сетках.
- После обновления данных снова просите фокус для того же ID, если элемент остался.
- Если его нет, заранее выберите понятную замену: ближайший сосед, первый элемент или родитель.

## Частые ошибки

| Ошибка | Что сделать |
|---|---|
| `focusRequester` и `onFocusChanged` стоят на каждой кнопке | Добавляйте их, лишь когда фокус надо запросить или наблюдать |
| `requestFocus()` вызван в теле composable-функции | Перенесите в `LaunchedEffect` |
| Начальный фокус привязан к `Unit`, а цель появляется позже | Привяжите к готовности или видимости цели |
| Запросы фокуса хранятся по индексу ленивого списка | Храните по постоянному ID |
| У всех элементов свои `focusProperties` | Дайте поиску по положению работать; меняйте лишь неверные переходы |
| Обработчик возвращает `true` для любой клавиши | Поглощайте лишь обработанные клавиши |
| Тесты нажимают элементы мышью в интерфейсе телевизора или крестовины | Посылайте нажатия клавиш и проверяйте фокус |

## Тесты

Проверяйте фокус через действия пользователя:

```kotlin
composeTestRule.onNodeWithTag("screen").performKeyInput {
    pressKey(Key.DirectionDown)
}

composeTestRule.onNodeWithTag("play-button").assertIsFocused()
```

Предпочитайте проверку семантики фокуса внешнему виду. Снимки экрана годятся для проверки вида фокуса, но не того, какой элемент им владеет.

Как выбирать вид теста — интерфейсный или общий, с упором на семантику, — см. [`compose-ui-testing-patterns`](../compose-ui-testing-patterns/SKILL.md).

## Тревожные признаки

- Для интерфейса с клавиатурой или пультом говорят: «Если нажать пальцем, фокус верный».
- Начальный фокус работает лишь с готовыми данными, но ломается после загрузки или обновления.
- Фокус выводят из выбранного элемента, хотя выбор и фокус — разные вещи.
- Переходы фокуса описаны в комментариях, но не заданы в коде и не проверены.

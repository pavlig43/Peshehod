# Правила проверки анимации

Восемь тем проверки: что искать в каждой и какие точные значения приводить в находках и планах. Основано на подходе Эмиля Ковальского к дизайну интерфейсов ([emilkowal.ski](https://emilkowal.ski/)). Значения отсюда не прикидывайте на глаз — копируйте.

## 1. Цель и частота

Для каждой анимации спросите: «Зачем она движется?» Целью может быть связь с местом, показ состояния, отклик, объяснение или смягчение резкой смены. Для часто видимого элемента «выглядит круто» не цель.

| Частота | Решение |
| --- | --- |
| Более 100 раз в день (горячие клавиши, открытие списка команд) | Без анимации. Всегда. |
| Десятки раз в день (наведение, переход по списку) | Убрать или сильно сократить |
| Изредка (модальные окна, боковые панели, уведомления) | Обычная анимация |
| Редко или впервые (знакомство с продуктом, отклик, празднование) | Допустим яркий эффект |

Ищите движение после нажатия горячих клавиш, анимацию открытия и закрытия списка команд (у Raycast её нет — это верно), украшения строк и отклик наведения, которые срабатывают постоянно. Часто лучшая правка — **удалить анимацию**.

## 2. Кривая и длительность

Порядок выбора кривой:

- Появление и исчезновение → **`ease-out`**: быстрый старт даёт живой отклик.
- Перемещение и смена формы на экране → **`ease-in-out`**.
- Наведение и смена цвета → **`ease`**.
- Непрерывное движение (бегущая строка, прогресс) → **`linear`**.
- По умолчанию → **`ease-out`**.

**`ease-in` в интерфейсе всегда находка**: медленный старт задерживает момент, за которым смотрит пользователь. Стандартные кривые CSS слишком слабы для выразительного движения. В плане предлагайте более заметные свои кривые как общие переменные по правилам проекта:

```css
--ease-out: cubic-bezier(0.23, 1, 0.32, 1);        /* strong ease-out for UI */
--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1);    /* strong ease-in-out for on-screen movement */
--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1);     /* iOS-like drawer curve */
```

Лимит длительности: **анимация интерфейса короче 300 мс**.

| Элемент | Длительность |
| --- | --- |
| Отклик на нажатие кнопки | 100–160 мс |
| Подсказка, небольшое всплывающее окно | 125–200 мс |
| Выпадающее меню, выбор | 150–250 мс |
| Модальное окно, боковая панель | 200–500 мс |
| Реклама или пояснение | Может быть дольше |

Ищите `ease-in` где угодно, простой `ease`/`linear` при появлении, длительность больше 300 мс для элементов интерфейса, задержку плюс анимацию для каждой подсказки на панели инструментов (после первой они должны появляться сразу).

## 3. Физичность и точка начала

- **Никогда не берите `scale(0)`**: в мире предмет не возникает из ничего. Цель: `scale(0.9–0.97)` вместе с `opacity: 0`.
- **Всплывающие окна, меню и подсказки растут от элемента, который их открыл**, а не от центра:
  ```css
  .popover { transform-origin: var(--radix-popover-content-transform-origin); } /* Radix */
  .popover { transform-origin: var(--transform-origin); }                       /* Base UI */
  ```
  **Модальные окна — исключение**: они появляются по центру, и `transform-origin: center` для них верен. Не отмечайте это как ошибку.
- **Отклик на нажатие**: `transform: scale(0.97)` у `:active` с `transition: transform 160ms ease-out`. Эффект должен быть слабым (0.95–0.98).

Ищите `scale(0)`, появление лишь через прозрачность без начального сдвига, `transform-origin: center` (или его отсутствие) у элементов, привязанных к кнопке, и кнопки без отклика на нажатие.

## 4. Возможность прервать движение

Переходы CSS (**transitions**) при новом действии продолжают путь из текущего состояния; ключевые кадры (**keyframes**) запускаются с начала. Всё, что часто вызывают или могут отменить на полпути — цепочки уведомлений, переключатели, перетаскивание, раскрытие, — должно работать на переходах или пружинах.

- Появление без JS: `@starting-style`; старый запасной способ — атрибут `data-mounted`, который задаётся в `useEffect`.
- Движению от жеста нужна пружина: при прерывании она сохраняет скорость.
- Рекомендуемые настройки пружины в стиле Apple: `{ type: "spring", duration: 0.5, bounce: 0.2 }`. Отскок держите слабым (0.1–0.3); заметный оставьте для смахивания и игровых моментов.
- **Разное время у фаз**: осознанные действия — нажатие, удержание, подтверждение удаления — идут медленнее; ответ системы приходит быстро. Одинаковое время нажатия и отпускания — находка.

Ищите `@keyframes` у уведомлений, переключателей и часто вызываемых элементов; жесты на кадрах фиксированной длительности; перетаскивание без учёта скорости при закрытии (ориентир `Math.abs(distance)/elapsedMs > ~0.11`, а не лишь путь); резкую остановку у края вместо растущего сопротивления.

## 5. Скорость работы

- **Анимируйте лишь `transform` и `opacity`.** `width`/`height`/`margin`/`padding`/`top`/`left` заново считают макет, рисуют и собирают кадр.
- **`transition: all`** оживляет лишние свойства вне GPU — это всегда находка.
- **Короткие свойства Framer Motion `x`/`y`/`scale` не ускоряются железом**: они идут в главном потоке и теряют кадры под нагрузкой. Цель — полная строка преобразования: `animate={{ transform: "translateX(100px)" }}`.
- **Не задавайте преобразования дочерних элементов через переменную CSS на родителе**: это заставляет пересчитывать стили всех потомков. Задавайте `transform` прямо элементу.
- CSS и WAAPI держатся под нагрузкой лучше JS на rAF. Для заранее известного движения берите CSS, для меняющегося и связанного с жестом — JS или пружину.
- При переходе держите `filter: blur()` меньше 20px: сильное размытие дорого, особенно в Safari.

Ищите `transition: all`, анимацию размеров и положения макета, короткие свойства Framer Motion на загруженных страницах, `setProperty('--x', …)` для движения потомков и циклы rAF там, где хватит CSS.

## 6. Доступность

```css
@media (prefers-reduced-motion: reduce) {
  .element { animation: fade 0.2s ease; } /* keep opacity/color, drop movement */
}
@media (hover: hover) and (pointer: fine) {
  .element:hover { transform: scale(1.05); } /* touch fires false hovers on tap */
}
```

Уменьшение движения значит меньше и мягче, **а не полное отсутствие** анимации. Оставьте переходы, которые помогают понять действие; уберите смену положения. В JS возьмите `useReducedMotion()` и задавайте разные значения преобразований.

Ищите движение без учёта `prefers-reduced-motion`, эффекты `:hover` без проверки типа указателя и режим уменьшенного движения, который убирает вообще весь отклик.

## 7. Цельность и общие переменные

- Движение должно подходить характеру продукта: игровой интерфейс может больше пружинить, рабочая панель остаётся собранной. Разный характер соседних компонентов — находка.
- Кривые и длительность храните в общих переменных. Пять вручную заданных почти одинаковых cubic-bezier — повод объединить их.
- Когда группа появляется сразу вся, а уместна **задержка 30–80 мс между элементами**, примените её. Это украшение не должно блокировать действия.
- Резкая смена прозрачности с двумя видимыми состояниями может быть мягче при `filter: blur(2px)` во время перехода.

Ищите повторяющиеся почти одинаковые кривые и длительность, один прыгучий компонент в строгом приложении, списки и сетки без задержки между элементами, а также смену кадров с заметным наложением двух состояний.

## 8. Упущенные места

Здесь ищут места, где движения нет, но оно нужно:

- Состояние меняется скачком — текст заменяется или макет прыгает, хотя короткий переход снял бы резкость.
- Пространственно связанный элемент, например панель от кнопки, появляется без движения, которое объяснило бы, откуда он взялся.
- Редкий эмоциональный момент — первый запуск, успех, праздник — лишён уместного яркого отклика.
- Для таких случаев пригодятся проценты `translate` (`translateY(100%)` равно высоте самого элемента) и раскрытие через `clip-path: inset()`, без жёстких сдвигов в пикселях.

Сообщайте лишь о нескольких таких местах, найденных в настоящих сценариях пользователя. Не делайте список пожеланий.

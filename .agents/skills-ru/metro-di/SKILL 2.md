# Metro DI

## Назначение

Этот навык помогает выбрать верную схему Metro до правки Kotlin и Gradle. Выбирайте самую простую правку Metro, подходящую устройству проекта: один модуль, несколько модулей или Kotlin Multiplatform.

## Порядок работы

1. Изучите устройство проекта, прежде чем предлагать код Metro.
2. Выясните, что перед вами:
   - проект Kotlin/JVM или Android с одним модулем;
   - проект из нескольких модулей, которому нужно объединять привязки;
   - Kotlin Multiplatform с `commonMain` и наборами исходников платформ.
3. Определите вид задачи:
   - первая настройка Metro;
   - добавление или правка привязок;
   - создание или расширение графа;
   - исправление места платформенного графа в KMP.
4. Перед нетривиальной правкой Metro прочитайте [references/metro-docs.md](references/metro-docs.md).

## Правила выбора

### Первая настройка

- Предпочитайте плагин Gradle:

```kotlin
plugins {
  kotlin("multiplatform") // либо jvm, android и т. д.
  id("dev.zacsweers.metro")
}
```

- Считайте, что плагин Gradle сам подключает плагин компилятора и библиотеку времени работы, если проект уже не управляет файлами Metro вручную.
- Для простого создания графа берите `createGraph<GraphType>()`.
- Берите `@DependencyGraph.Factory`, лишь когда нужны входные данные времени работы или включаемые привязки.

### Проект с одним модулем

- Если граф и реализации живут рядом и объединять модули не нужно, предпочитайте явные `@Binds` или `@Provides`.
- Для классов с внедрением через конструктор берите `@Inject`.
- Если границы модулей не требуют объединения, держите граф простым и местным.

### Проект из нескольких модулей

- Предпочитайте объединение по области действия через `@ContributesBinding` и `@ContributesTo`.
- Рассматривайте `@DependencyGraph(scope = ...)` как место слияния вкладов из других модулей.
- Для пар API и реализации, которые должны находиться автоматически между модулями, берите `@ContributesBinding`.
- Для контейнеров привязок и интерфейсов провайдеров, которые вносят вклад в область графа, берите `@ContributesTo`.
- Не возвращайте местный `@Binds` для каждой добавленной реализации, если схема модуля не требует привязок без объединения.

### Kotlin Multiplatform

- Различайте общие контракты и конечные графы платформ.
- Если есть вклады отдельных платформ, не кладите конечный `@DependencyGraph` в `commonMain`.
- Предпочтительная схема:
  - общий контракт графа в `commonMain` без `@DependencyGraph`;
  - `AndroidAppGraph`, `JvmAppGraph`, `IosAppGraph` и прочие в наборах исходников платформ;
  - аннотация `@DependencyGraph` на графе каждой платформы.
- Metro объединяет лишь то, что видно из соответствующего набора исходников.

### `expect` / `actual`

- Не придумывайте для Metro `expect fun createGraph()`, если проект уже не использует эту схему осознанно.
- Берите `expect` / `actual` для платформенных реализаций и API, а не для обхода правил размещения графа Metro.
- Если зависимость различается по платформам, держите интерфейс или контракт использования в `commonMain`, а платформенную реализацию привязывайте или предоставляйте в наборе исходников платформы, где находится конечный граф.
- Если аннотации стоят на объявлениях `expect` / `actual`, до правки соседнего кода проверьте, нужна ли аннотация также на `actual`.

## Предохранители

- Не кладите общий `@DependencyGraph` в `commonMain`, если ему нужны вклады отдельных платформ.
- Не объявляйте KAPT или KSP обязательной частью настройки Metro. Metro работает через плагин компилятора.
- Не считайте `@ContributesBinding` всегда лучше `@Binds`: смотрите на границы модулей.
- Не создавайте лишний слой, если хватает `createGraph()` или имеющейся фабрики графа.
- Не переносите код Metro в посторонние модули без прямого требования перестроить схему проекта.

## Что проверить

- Где объявлен нужный граф.
- Какому набору исходников принадлежит каждая реализация.
- Виден ли привязываемый тип из набора исходников графа.
- Использует ли проект области действия для объединения.
- Какая форма лучше передаёт смысл привязки:
  - внедрение через конструктор;
  - `@Provides`;
  - `@Binds`;
  - `@ContributesBinding`;
  - `@ContributesTo`.

## Справка

Читайте [references/metro-docs.md](references/metro-docs.md) о настройке плагина и создании графа, выборе привязок для одного или нескольких модулей, размещении графа KMP и применении `expect` / `actual`.

## Как писать ответ

- Сначала объясните правки Metro через устройство проекта, затем называйте нужные аннотации и изменения Gradle.
- Для KMP ясно укажите, в каком наборе исходников должен быть конечный граф и почему.
- Для нескольких модулей явно назовите область объединения и границы модулей, которые вносят вклад.

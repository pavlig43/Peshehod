# Справка по Metro DI

Используйте её, когда нужны точные сведения о Metro, а не общий ответ про внедрение зависимостей.

## 1. Настройка и запуск

Обычно Metro подключают плагином Gradle:

```kotlin
plugins {
  kotlin("multiplatform") // либо jvm, android и т. д.
  id("dev.zacsweers.metro")
}
```

Как правило, плагин сам добавляет библиотеку Metro для времени работы и подключает плагин компилятора.

Входной точкой служит граф зависимостей:

```kotlin
@DependencyGraph(AppScope::class)
interface AppGraph {
  val repository: Repository
}
```

Создайте его так:

```kotlin
val graph = createGraph<AppGraph>()
```

Берите `@DependencyGraph.Factory`, лишь если графу нужны входные данные времени работы — например, экземпляры `@Provides` или зависимости `@Includes`.

## 2. Выбор способа привязки

### Предпочитайте местные явные привязки, если:

- проект по сути состоит из одного модуля;
- граф и реализация живут рядом;
- не нужно объединять вклады нескольких модулей.

Обычно нужны:

- `@Inject` для классов с внедрением через конструктор;
- `@Provides` для сторонних типов и типов фреймворка;
- `@Binds` для явной связи интерфейса с реализацией.

### Предпочитайте объединение, если:

- привязки находятся в модулях функций или библиотек;
- конечный граф должен находить вклады сам;
- схема внедрения зависимостей уже строится вокруг областей действия.

Обычно нужны:

- `@ContributesBinding(scope)` для привязки реализации к интерфейсу;
- `@ContributesTo(scope)` для интерфейсов провайдеров или контейнеров привязок, которые вносят вклад.

Место слияния — область графа:

```kotlin
@DependencyGraph(AppScope::class)
interface AppGraph
```

Значит, вклады в `AppScope` из других модулей попадут в созданный граф.

## 3. Несколько модулей

Для проекта из нескольких модулей:

- задайте постоянную область действия, общую для графа и модулей-участников;
- держите реализации в модулях, которым они принадлежат;
- добавляйте их через `@ContributesBinding` или `@ContributesTo`;
- держите конечный `@DependencyGraph` в модуле приложения или корне сборки.

Для разделения API и реализации предпочитайте такую схему:

```kotlin
interface Repository

@ContributesBinding(AppScope::class)
@Inject
class RepositoryImpl(...) : Repository

@DependencyGraph(AppScope::class)
interface AppGraph {
  val repository: Repository
}
```

Если у класса несколько родительских типов или нужный тип привязки неочевиден, явно задайте `binding = binding<Interface>()`.

## 4. Правила Kotlin Multiplatform

Библиотека Metro и создание кода не зависят от платформы, но видимость набора исходников всё равно важна.

Главное правило: если графу нужны вклады отдельных платформ, конечный `@DependencyGraph` должен жить в наборе исходников платформы.

Предпочтительная схема:

```kotlin
// commonMain
interface AppGraph {
  val httpClient: HttpClient
}

// androidMain
@DependencyGraph
interface AndroidAppGraph : AppGraph {
  @Provides
  fun provideHttpClient(): HttpClient {
    return HttpClient(OkHttp)
  }
}

// jvmMain
@DependencyGraph
interface JvmAppGraph : AppGraph {
  @Provides
  fun provideHttpClient(): HttpClient {
    return HttpClient(Netty)
  }
}
```

Так общий контракт остаётся прежним, а граф каждой платформы видит её привязки. Не кладите конечный `@DependencyGraph` в `commonMain`, если нужны вклады из `androidMain`, `iosMain`, `jvmMain` или другого платформенного набора.

## 5. Как применять `expect` / `actual`

Сам по себе Metro не причина вводить `expect` / `actual`. Они нужны, лишь когда предметная область и правда требует платформенных API или реализаций.

Предпочтительное разделение:

- `commonMain`: интерфейсы, сценарии работы и контракты графа без аннотации конечного платформенного графа;
- наборы исходников платформ: реализации `actual`, платформенные провайдеры и конечные графы, когда нужны платформенные привязки.

Подходящие случаи:

- `expect` для журнала, файловой системы, сведений об устройстве, диспетчера или обёртки над платформенным сервисом;
- класс `actual`, добавленный в граф или предоставленный в наборе исходников платформы.

Неподходящие случаи:

- `expect fun createGraph()` лишь для обхода неверного размещения графа;
- аннотация общего графа, который не видит вклады платформы.

При правке кода с `expect` / `actual` проверьте, должна ли аннотация стоять и на объявлении `actual`; не считайте, что хватает общего объявления.

## 6. Частые ошибки

- Настраивать Metro так, словно для него нужен KAPT или KSP.
- Брать `@ContributesBinding` для местной привязки в одном модуле, когда яснее `@Binds`.
- Держать граф в `commonMain` и ждать, что он найдёт привязки отдельных платформ.
- Скрывать владельца платформенного кода, размещая провайдеры не в том наборе исходников.
- Создавать лишние слои вокруг графа, когда хватает `createGraph()` или готовой фабрики.

## 7. Быстрый выбор

- Один простой модуль приложения: `@Inject`, `@Provides`, `@Binds`, `createGraph()`.
- Несколько модулей с общей областью: `@ContributesBinding` / `@ContributesTo` и `@DependencyGraph` с этой областью.
- KMP с реализациями отдельных платформ: общие контракты в `commonMain`, конечный граф — в каждом платформенном наборе.
- KMP с `expect` / `actual`: берите их для платформенных API и реализаций, а не вместо правильного размещения графа Metro.
